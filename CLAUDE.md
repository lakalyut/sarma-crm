# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

«Пульс» — внутренняя CRM для аналитики продаж (кальянные табаки): импорт продаж из XLSX,
сопоставление сырых номенклатур со справочником товаров, аналитика по клиентам/городам,
ABC-рейтинг ассортимента, амбассадорские отчёты. Русскоязычный интерфейс и код (докстринги,
переменные в шаблонах, коммиты — на русском).

Живой план работ — [ROADMAP.md](ROADMAP.md). Разбор дизайн-системы (токены/компоненты/
известные ловушки каскада CSS) — [DESIGN.md](DESIGN.md). **Оба файла намеренно не в git**
(исключены через `.git/info/exclude` — локальный, невersioned exclude-файл конкретной
рабочей копии, не `.gitignore`). При клонировании репо на другой машине ни один не
появится сам — их нужно перенести отдельно (скопировать вручную/через облако) и на новой
машине тоже добавить в `.git/info/exclude`, если они должны остаться вне истории.

## Commands

Windows/venv (как настроено в этом репозитории — `venv/` в корне):

```powershell
venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8001   # dev-сервер
venv\Scripts\pytest.exe -q                                              # тесты
venv\Scripts\black.exe .                                                # форматирование
venv\Scripts\ruff.exe check . --fix                                     # линт с автофиксом
venv\Scripts\alembic.exe upgrade head                                   # применить миграции
venv\Scripts\alembic.exe revision --autogenerate -m "описание"          # новая миграция
```

Кроссплатформенные шорткаты — `make fmt` / `make lint` / `make test` (см. [Makefile](Makefile)).

Один тест: `pytest tests/test_smoke.py::test_root_redirect -q`.

`.claude/launch.json` поднимает dev-сервер на порту **8001** (не 8000 — тот занят под
docker-compose/prod-контейнер), через Browser-preview инструмент (`preview_start` с
`name: "sarma-web"`), а не через Bash напрямую.

**`--reload` не всегда подхватывает правки `.py`-файлов в этом окружении** —
поймано многократно: меняешь `app/services/*.py` или `app/routes/*.py`, а
сервер продолжает отвечать по старому коду (в логах ни одного "Reloading").
Шаблоны (`.html`, Jinja auto-reload) и статика (`.css`/`.js`, читаются с диска
на каждый запрос) подхватываются нормально — проблема именно с Python-модулями.
После правки `.py`-файла — `preview_stop` + `preview_start` заново, не
надеяться на `--reload`.

## Local setup

- Реальная БД разработки — SQLite (`main.db` в корне, в `.gitignore`), схема накатывается
  через alembic (`alembic upgrade head`), а не автосозданием. Автосоздание через
  `Base.metadata.create_all()` есть в [app/main.py](app/main.py), но включается только
  флагом `AUTO_CREATE_SCHEMA=1` — по умолчанию выключено, используется только миграция.
- `.env` (в `.gitignore`, шаблон — `.env.example`) содержит `ADMIN_EMAIL`/`ADMIN_PASSWORD` —
  при старте приложения [app/startup.py](app/startup.py) `ensure_admin()` гарантирует, что
  такой admin-пользователь существует и активен (создаёт или чинит роль/пароль/статус).
- Прод — Postgres + Docker Compose (`docker-compose.yml`: db/web/nginx/certbot),
  `docker-compose.dev.yml` — Postgres в докере + приложение с `--reload` на 8000.
- **Тесты** ([tests/](tests/), 34 штуки на 2026-08-02, было ровно один smoke-тест) — фикстуры в
  [tests/conftest.py](tests/conftest.py). Изолированной схемы через `Depends(get_db)`-override
  на роуте **недостаточно** — `app/render.py` и обработчики ошибок в `app/main.py` создают
  свою `SessionLocal()` в обход dependency injection (см. выше). Рабочее решение: conftest
  направляет сам глобальный `DATABASE_URL` на `sqlite:///./test.db` (`os.environ.setdefault`
  до первого импорта `app.database`, тот же файл, что и CI) и пересоздаёт схему
  (`drop_all`/`create_all`) в фикстуре `db_session` перед каждым тестом — тогда роуты,
  `render()` и обработчики ошибок совместно смотрят в одну и ту же БД без хирургии с
  overrides. Фикстуры `client`/`admin_user`/`admin_client` — готовый залогиненный
  `TestClient`; `client`/`admin_client` сразу выставляют cookie `csrf_token` (фиксированный
  тестовый `CSRF_TOKEN` в `conftest.py`) — любой POST-тест обязан передавать
  `data={"csrf_token": CSRF_TOKEN, ...}`, иначе получит 403 от `csrf_guard` (см. Auth ниже),
  а не ту ошибку, которую тест на самом деле проверяет.

## Architecture

**Роуты — тонкие, бизнес-логика — в `app/services/`.** Каждый файл в
[app/routes/](app/routes/) — один `APIRouter` на раздел (`analytics`, `products`, `imports`,
`admin_users`, `admin_abc`, `admin_regions`, `admin_imports`, `client_analysis`, `dashboard`,
`events`, `misc`), подключается в
[app/main.py](app/main.py). Роуты парсят query/form-параметры, зовут функцию из
`app/services/*_service.py` (SQLAlchemy-запросы и агрегация), рендерят шаблон.
`routes/ambassadors.py` (раздел «Амбассадорские отчёты») удалён — механика (SKU-статусы
по многим клиентам) сейчас частью `client_analysis.py`, см. ниже.

**Рендеринг страниц идёт через [app/render.py](app/render.py)** — хелпер `render(request,
template, ctx)`, который сам достаёт `current_user` по cookie-сессии и кладёт его в контекст
шаблона. Все роуты импортируют именно его (`from ..render import render`). **В
[app/main.py](app/main.py) есть собственная копия функции `render()` — она не используется
нигде** (обработчики ошибок 401/403/404/500 в main.py дергают `templates.TemplateResponse`
напрямую); не путать эти две функции при правке рендеринга.

**Auth — самодельная, без сторонних auth-фреймворков**: `session_id` в httponly-cookie →
строка в таблице `sessions` ([app/auth_models.py](app/auth_models.py)) с TTL 14 дней.
[app/auth_deps.py](app/auth_deps.py) даёт FastAPI-зависимости `get_current_user` /
`require_user` / `require_admin` / `require_analyst` (`role in ("admin", "user")` —
блэнкет-доступ на аналитику) / `require_ambassador` (`role in ("admin", "ambassador")`,
горизонт 13, см. ниже). Три роли на `User.role`: `admin`/`user`/`ambassador`. Пароли —
прямой `bcrypt`
([app/auth_security.py](app/auth_security.py), `passlib` убран — был мёртв с 2020, роадмап
давно планировал; существующие хеши в БД совместимы без миграции, оба формата `$2b$12$...`).
Пароль усекается до 72 байт перед хешированием/проверкой — `bcrypt` 5.0 **бросает
исключение** на более длинных, а не молча режет, как раньше делал `passlib`. Установка
пароля новому пользователю — одноразовый токен (`PasswordToken`, SHA-256 хэш токена в БД),
ссылку админ копирует вручную со страницы пользователей — SMTP-отправки нет.

**Удаление пользователей** — `POST /admin/users/{id}/delete`
([app/routes/admin_users.py](app/routes/admin_users.py)): нельзя удалить самого себя,
нельзя удалить амбассадора с историей визитов (`Visit.ambassador_id`, `nullable=False` —
реальные бизнес-данные для лидерборда, не служебная запись; отключение — штатный способ
убрать доступ без потери данных). Сессии и `PasswordToken` пользователя удаляются,
`EventLog.user_id` обнуляется (история импортов остаётся без привязки к автору). Кнопка в
`users_list.html` — с `onsubmit="return confirm(...)"`, единственное место в проекте с этим
паттерном (ни у одной другой формы подтверждения нет — здесь оправдано необратимостью).

**Rate-limit на `/auth/login` — по email, не по IP.** Таблица `login_attempts`
(`LoginAttempt` в `auth_models.py`) — строка на каждую неудачную попытку. Перед
`verify_password()` считаются неудачные попытки по email за последние 15 минут; 5 и
больше — блок без похода в bcrypt. Осознанно не по IP: за приложением стоит nginx
([deploy/nginx.conf](deploy/nginx.conf)), `request.client.host` в контейнере всегда был бы
адресом прокси, а не клиента — понадобилась бы отдельная настройка доверия к
`X-Forwarded-For`/`X-Real-IP`, не делали.

**CSRF — double-submit cookie, без сторонней зависимости**
([app/csrf.py](app/csrf.py)): httponly-cookie `csrf_token` (`secrets.token_urlsafe(32)`,
выставляется в `render()` и в собственном `_render()` внутри `auth_routes.py` — там свои
прямые `TemplateResponse`, минуя общий `render()`) сверяется с одноимённым полем формы.
Поле само добавляется в каждую `<form method="post">` через глобальный
[csrf.js](app/static/js/csrf.js) (тот же паттерн, что `custom_select.js`/
`checkbox_multiselect.js`/`region_memory.js` — подключён в `base.html`, и отдельно в
`base_auth.html` для логина/сброса пароля, у той пары свой скелет без сайдбара) — не
нужно вручную трогать каждый из ~12 шаблонов с формами.
**Реализовано не через `@app.middleware("http")`, а через FastAPI-зависимость уровня
приложения** (`FastAPI(dependencies=[Depends(csrf_guard)])`) — важная ловушка, пойманная
эмпирически: `BaseHTTPMiddleware` в Starlette 0.37 не реплеит тело запроса корректно для
повторного `request.form()` внутри самого роута — мидлварь-версия видела поля формы у себя,
а роут после неё получал пустые значения (воспроизводится в одну функцию, без реального
приложения). Зависимость работает с тем же объектом `Request`, что и `Form(...)`-параметры
роута — `request.form()` кеширует результат на самом объекте, повторное чтение безопасно.
`verify_csrf()` сравнивает через `secrets.compare_digest()` **как bytes, не str** —
голый `str`-вариант падает `TypeError` на не-ASCII токене вместо `False`.
**Эндпоинты с header-based аутентификацией** (Telegram `initData`, не cookie-сессия —
`app/telegram_auth.py::get_current_ambassador`, см. горизонт 13 ниже) собраны в
`CSRF_EXEMPT_PATHS` (`app/csrf.py`) — обычный CSRF там неприменим по построению, подделать
заголовок с валидной подписью без знания токена бота нельзя.
**Обработчики ошибок (401/403/404/500 в `app/main.py`) — отдельная, третья точка рендеринга
шаблонов** (не `render()`, не `_render()` из `auth_routes.py`): `_render_error()` в
`main.py` дублирует их логику (`csrf_token` в контекст + `attach_csrf_cookie()`) для
403/404/500 — раньше не дублировала, `templates.TemplateResponse` звался напрямую без
`csrf_token` вообще, и `csrf.js` подставлял в любую форму на странице ошибки (включая
логаут в сайдбаре — `errors/403.html` расширяет `base.html`) пустое значение, которое не
совпадало с cookie: `POST /auth/logout` сам получал 403, тупик без выхода со страницы
ошибки. Поймано вживую на роли с урезанным доступом (`ambassador`) — у `admin`/`user`
почти нет страниц без доступа, баг был невидим до амбассадоров. `401` не задет — чистый
редирект на `/auth/login`, шаблон не рендерится вообще.

**Импорт и сопоставление номенклатуры** — сердце домена:
[app/product_parser.py](app/product_parser.py) нормализует строки (нижний регистр, ё→е, чистка
скобок/спецсимволов) и матчит сырое название продажи (`raw_name` из XLSX) на товар из
справочника (`Product`) через `rapidfuzz.fuzz.WRatio` с порогом score **70**. Пайплайн:
[app/routes/imports.py](app/routes/imports.py) `POST /import-xlsx` — расширение файла (`.xlsx`)
и размер (лимит **20 МБ**, `MAX_IMPORT_FILE_SIZE`) проверяются до чтения в pandas (nginx
режет на 50 МБ отдельно — это не экономия памяти, цель именно не пускать файлы 20-50 МБ в
`pd.read_excel()`), читает XLSX через pandas,
требует колонки `Месяц/Тип/Клиент/Номенклатура/SKU/Количество/Вес`, для каждой строки зовёт
`match_product_by_flavor()`; при совпадении проставляет `product_id/sku/name/matched=True`,
иначе `matched=False` — такие строки видны на `/admin/unmatched`
([app/routes/analytics.py](app/routes/analytics.py)) и **пока не редактируются на месте**
(это горизонт 1 роадмапа — сейчас read-only список сырых строк).

**Данные продаж — плоская таблица `Sale`** ([app/models.py](app/models.py)): город, месяц
(строка `YYYY-MM-01`, форматируется фильтром Jinja `format_month` в «Март 2026»), тип точки,
клиент, сырые и сопоставленные название/SKU, qty/weight, `matched`. Почти вся аналитика —
это `GROUP BY` по `Sale` с общим набором SQLAlchemy-фильтров из
[app/services/sale_filters.py](app/services/sale_filters.py) (`build_sale_filters`), который
собирают `routes/analytics.py` и `services/client_analysis_service.py`/`dashboard_service.py`
по параметрам `city`/`months`/`sale_types`/`client`/`matched`. Есть и списочные варианты
`cities`/`clients` (в дополнение к одиночным `city`/`client`, не вместо) — под дашборд и
«Анализ по клиентам», которые умеют фильтровать сразу по нескольким регионам/клиентам.
Два составных индекса (миграция `0ff0c95eb616`, горизонт 12 ROADMAP.md):
`ix_sales_city_month` (city, month) — под `build_sale_filters()`, где `city`/`cities`
всегда первый фильтр, часто сразу с `months`; `ix_sales_city_client_type`
(city, client, type) — под точечные выборки вроде `get_client_detail_data`. До этого
на `sales` не было ни одного индекса, кроме PK — вся аналитика была full table scan.

**ABC-рейтинг** — не автоматический: категория (A/B/C) проставляется вручную per-товар
per-сегмент через `/admin/abc` в таблицу `product_abc_ratings`; сегменты (`AbcSegment`,
напр. HoReCa/Розница) создаются там же. Автоматический расчёт по правилу 80/15/5 — в
горизонте 3 роадмапа, ещё не сделан.

**Детализация по клиенту** (`/analytics/client`, роут в
[app/routes/analytics.py](app/routes/analytics.py), шаблон
[client_detail.html](app/templates/analytics/client_detail.html)) — вся клиентская
аналитика для одного клиента/города/типа точки в сворачиваемых карточках (`.amb-card`/
`.amb-toggle`, тот же паттерн, что и на «Анализе по клиентам» ниже): динамика по месяцам,
SKU-статусы (New/Lost/Unstable — `build_client_sku_status()` в
[app/services/ambassadors_service.py](app/services/ambassadors_service.py), с фильтром по
`sale_type` страницы и колонкой ABC из `rating_by_product`, сортировка по клику на месяц/
Итого/**Статус**/**ABC** — числовые колонки сравниваются `parseFloat`, «Статус»/«ABC» через
отдельные компараторы по рангу значимости (`STATUS_RANK`/`ABC_RANK` в инлайновом JS), кнопки
фильтра статуса несут счётчик «Новые (10)» и т.п.), «Ассортимент по ABC» (гэп-анализ,
`abc_service.get_client_abc_overview`), сводные карточки, график (Chart.js, чекбоксы-метрики
Количество/Вес/Уникальные SKU, переключатель Линия/Гистограмма). Настройки
порогов SKU-статусов (`new_client_months`/`lost_months`/`unstable_gap_months`) — через
`get_int_param()` в [app/utils/params.py](app/utils/params.py).

**«Анализ по клиентам»** (`/analytics/client-analysis`,
[app/routes/client_analysis.py](app/routes/client_analysis.py) +
[app/services/client_analysis_service.py](app/services/client_analysis_service.py)) — две
вкладки на одной странице, переключение обычной GET-навигацией (`?tab=summary`/
`?tab=ambassadors`): сервер каждый раз считает и рендерит **только** активную вкладку
(вторая ветка Jinja не выполняется), поэтому одноимённые JS-хелперы вроде `initTagSearch`
в шаблонах вкладок не конфликтуют друг с другом.
- «Свод» — иерархия тип точки → клиент → номенклатура с ленивой подгрузкой
  (`/api/client-analysis/{clients,nomenclature,missing}`), первый тип по весу — развёрнут
  сразу. Метрика переключается вкладкой (Вес/Количество/Уникальных SKU) мгновенно на
  клиенте — каждая lazy-строка везёт сразу все метрики, повторного запроса на клик нет.
  ABC-сегмент — **свой на каждый тип точки** (не общий на всю страницу — наименования
  типов разнятся по регионам), дефолт через `abc_service.guess_default_segment()`, бейджи
  считает `get_abc_badges_for_clients()` (2 запроса на весь список клиентов типа, без
  N+1) — **не** рендерятся в свёрнутой строке клиента (перегружали список), а отдельной
  строкой `abcBadgesRowHtml()` сразу под именем при раскрытии карточки, общей для обеих
  под-вкладок (Номенклатуры/Чего не хватает), без лишнего запроса — данные уже есть.
  «Чего не хватает» — `get_client_abc_overview()` как есть. Сверху страницы — блок
  карточек-метрик (`.metric-card`, как на «Графиках»): все три метрики сразу
  (Вес/Количество/Уникальных SKU), специально **не** синхронизирован с переключателем
  метрики таблицы. Считает `get_summary_totals()` в `client_analysis_service.py` —
  помесячные итоги по всей текущей выборке без разбивки по типу точки; уникальные SKU —
  отдельный `count(distinct)` на месяц, не сумма по типам (тот же принцип, что и
  unique_clients/unique_sku на «Аналитике по регионам» ниже).
- «Амбассадорский отчёт» — SKU-статусы по нескольким клиентам сразу, **без** разбивки по
  типу точки (историческое поведение, восстановлено дословно из git-истории вместе с
  `build_ambassadors_report()`, а не по памяти) — отдельная от «Свода» механика, живёт
  в шаблоне-партиале [_client_analysis_ambassadors.html](app/templates/analytics/_client_analysis_ambassadors.html).
  С 2026-07-26 — колонка ABC (`build_ambassadors_report()` теперь резолвит `product_id` по
  SKU так же, как `build_client_sku_status()`) с одним общим селектором сегмента на всю
  вкладку (не per-тип, как на «Своде», — отчёт не разбит по типу точки, `abc_segment`
  query-параметр в роуте, `rating_by_product` строится тем же двухстрочным паттерном, что
  и `abc_service.get_abc_badges_for_clients`), плюс счётчики по статусам и сортировка по
  клику на «Статус»/«ABC» — тот же JS-паттерн, что и в детализации клиента выше, продублирован
  per-card (карточка на клиента), с учётом строки «Итого», которую нужно допереставлять
  после сортировки.

На странице «Клиенты» ([clients_summary.html](app/templates/analytics/clients_summary.html))

Каждая строка таблицы несёт `data-monthly` — помесячные qty/вес/SKU для мгновенного
(без похода на сервер) переключения метрики и мини-спарклайна, JS читает через
`row.dataset.monthly`. Формат — **позиционные триплеты** `[qty, weight, sku_count]`
(`_get_monthly_by_client()` в
[clients_service.py](app/services/clients_service.py)), не словари с именованными
ключами и не полем `month` — на крупном городе (1500+ строк) повтор имён ключей в
каждой раздувал страницу на сотни КБ (горизонт 12 ROADMAP.md). `METRIC_FIELD` в JS
поэтому — индексы массива (`{qty: 0, weight: 1, sku: 2}`), не имена полей; при
проверке принадлежности **обязательно** `field in METRIC_FIELD`, не
`METRIC_FIELD[field]` truthy-проверкой — индекс `0` (qty) в JS falsy, ловили этот
самый баг при переводе на позиционный формат.

регионов/городов промежуточная группировка `dims + client` может дать
десятки тысяч строк, транспортировать их все в Python и суммировать там —
дороже, чем сложить в БД одним запросом.

Тег-поиск «Регион» предлагает вместе с городами макро-регионы из справочника
`/admin/regions` (`Region`/`CityRegion`, [app/services/city_regions_service.py](app/services/city_regions_service.py)
— город входит только в один регион, простое присвоение, не матрица как у
ABC-сегментов). Выбор макро-региона схлопывает его города в одну строку/линию:
`get_regions_overview()` принимает `city_to_region_name`, подменяет `Sale.city`
на SQL `CASE` (город → имя региона) **до** `group by`, поэтому
`unique_clients`/`unique_sku` на объединённой строке — честный distinct по
объединению городов, не наивная сумма per-город чисел. Роут вызывает
`get_regions_overview()` дважды — `data` (со схлопыванием, обычный режим) и

реально выбран**: без него `city_to_region_name` пустой в обоих вызовах, результат
побайтово совпал бы, поэтому `detail_data = data` без повторного прохода по `sales`
(горизонт 12 ROADMAP.md — было ~1.7с на 39к строк из-за именно этого дублирования).
Оба набора кладутся в атрибуты
`data-regions`/`data-regions-detail` (`|tojson`, не сырым в `<script>` — см.
предупреждение про Jinja-автоэкранирование выше). На клиенте единственный
canvas переключается между `data`/`detail_data` по вкладке «Общий график» /
«По регионам отдельно» (обе — один и тот же многолинейный Chart.js-график,
просто разный источник строк; отдельной сетки мини-графиков на город больше
нет — убрали вместе с багом, когда её `display: grid` в dashboard.css,
подключённом позже base.css, перебивал `.is-hidden` при равной
специфичности) — плюс тумблер «Линия/Гистограмма» (`type` графика; с 2026-07-26 такой же

и «Амбассадорский отчёт» на «Анализе по клиентам», Дашборд); раньше цикл по `all_months`

(все `<input type="checkbox" name="months">` в DOM одновременно, для сохранения состояния
между годами), но видим — через `.is-hidden` — только один `.mp-year-grid` за раз; `‹`/`›`
в [checkbox_multiselect.js](app/static/js/checkbox_multiselect.js) листают `currentIndex`.

той стороне есть выбор) пересчитываются **на лету** из реального состояния чекбоксов при
каждом `change` — не статичный бейдж с сервера, иначе после клика цифра бы отставала (и

`change`, точечный `list.addEventListener("change", ...)` его не ловит).

**Внутри года месяцы отображаются в обратном к DOM-порядку направлении** — сетка читается
Январь→Декабрь слева направо/сверху вниз, хотя сами `<input>` в DOM идут по убыванию
(см. выше, `get_months(reverse=True)`) и должны оставаться в этом порядке — `checkbox_multiselect.js`
полагается на монотонность DOM-позиций сквозь все года разом для диапазона в закрытой
сводке. Решено **визуально**, не перестройкой DOM: `style="order: {{ loop.length -
loop.index0 - 1 }}"` на каждом `.mp-month-chip` (CSS `order` работает и в grid, влияет
только на раскладку `.mp-year-grid`, не на порядок обхода `querySelectorAll`) — если
понадобится похожая задача «показать в другом порядке, чем хранится», это готовый, уже
проверенный на этом ровно баге приём.

Разрозненный (не только диапазон) мультивыбор через года — обязательное требование,
пейджер только меняет навигацию, не семантику; закрытая сводка мультиселекта схлопывается
так же, как раньше: ≤3 месяцев — список через запятую, >3 подряд идущих — диапазон «месяц –
месяц», >3 вразнобой — «первые 3, +N» (порог 3, а не 2, как у обычных мультиселектов без
`dateRange` — пороги осознанно разные). Рядом на тех же 5 страницах есть ещё текстовая
подпись «Месяцы: ...» под фильтрами (`.selected-city-text`) — server-rendered, через
Jinja-фильтр `format_month_list` (`app/templating.py`).

**`Sale.month` хранит два формата одновременно — это нормально, не грязные данные.**
Часть городов грузится сразу со значением вида `«Май 2026»`, часть — как ISO
`2026-05-01`. `app/utils/dates.py` → `parse_month(value) -> (год, месяц) | None` — общий
парсер обоих форматов (заведён для `month_sort_key()` ещё в горизонте 4, но исходно не был
переиспользован больше нигде); `format_month`/`format_month_short`/`format_month_list`/
`group_months_by_year` в `app/templating.py` **обязаны** ходить через него, а не через
`datetime.fromisoformat()` напрямую — иначе города со вторым форматом либо тихо ломают
отображение (см. историю ниже), либо вообще проваливаются. `group_months_by_year()` кидает
всё, что `parse_month()` не смог разобрать, в отдельный бакет-год `"—"`, не смешивая его ни
с настоящими годами, ни разные неразобранные значения друг с другом. На клиенте
`checkbox_multiselect.js` про формат ничего не знает и знать не должно — DOM-порядок
чекбоксов уже хронологический (сервер сортирует `get_months(reverse=True)` через
`month_sort_key`), поэтому сортировка для диапазона/списка идёт по DOM-позиции
(`all.indexOf(...)`), а не `value.localeCompare(value)` — второе для «Месяц Год»-строк даёт
случайный алфавитный, а не хронологический порядок (нашли и починили заодно с пейджером,
тот же фикс задублирован в `admin/imports_delete.html`, у него отдельная копия
`updateText()` — не Jinja-цикл, месяцы грузит через AJAX после выбора города, `render()`
там же; пейджер на эту страницу пока не переносили, список остаётся плоским, follow-up).

**Известная асимметрия, не унифицирована:** JS-диапазон в закрытой сводке считает
«подряд» по смежности DOM-позиций **в списке доступных месяцев**, а `format_month_list()` в
Python — по календарной смежности (год,месяц). На городе с разреженными продажами (не
каждый месяц) это может разойтись: «выбрать всё» на JS-стороне даст диапазон «Январь 2024 –
Июль 2026» (все доступные месяцы выбраны подряд **в списке**), а серверная подпись «Месяцы:
...» — честный список с «+N» (календарных месяцев между ними не было). Оба алгоритма
корректны по своей логике, это разные логики, не одна и та же с багом.

**История (закрыто 2026-07-27): именно рассинхрон форматов `Sale.month` выше был причиной
и краша, и «работает криво».** Хронология: `format_month_list`/`next_month()` сперва
парсили только ISO без `try/except` → могли уронить страницу 500-й на «Месяц Год»-данных
(закрыто) → пользователь сообщил «работает криво» после деплоя (открытый вопрос) → новый
пейджер по годам показал наглядно (`m[:4]` на «Май 2026» даёт «Май», а не год — заголовки
групп были именами месяцев, не годами) → пользователь подтвердил формат данных → настоящий
фикс через общий `parse_month()`. Если увидите новый странный баг рядом с месяцами —
проверяйте именно этот угол первым, а не гипотетические новые причины.

вид `<select>`/поиска в строках фильтров, устранение хардкод-hex, вынос повторяющихся
инлайн-стилей в классы) сделаны — см. горизонт 2.5 в ROADMAP.md.

**Gzip на все ответы** — `app.add_middleware(GZipMiddleware, minimum_size=1000)` в
[app/main.py](app/main.py). Ни nginx ([deploy/nginx.conf](deploy/nginx.conf)), ни
FastAPI сжатием не занимались вообще — большие аналитические HTML-страницы (много
однотипных строк таблицы — одни и те же имена классов/атрибутов повторяются сотни
раз) жмутся в 15-25×, добавлено горизонтом 12 ROADMAP.md после жалобы на скорость
загрузки.

**Амбассадорские визиты (горизонт 13)** — полевые амбассадоры демонстрируют
клиентам ароматы, CRM считает лидерборд и сверяет продемонстрированное с
заказанным. Данные: `Visit`/`VisitProduct` ([app/models.py](app/models.py),
`ambassador_id`/`city`/`client`/`sale_type`/`created_at`, `created_at` —
настоящий `datetime`, единственный формат, в отличие от `Sale.month`) и три
новых поля на `User` ([app/auth_models.py](app/auth_models.py)):
`telegram_id` (unique, nullable), `city` (обычная строка — той же природы,
что `Sale.city`, не FK на справочник; заменил `region_id` в ходе сессии,
см. ROADMAP.md «Горизонт 13.3» — амбассадор привязан к одному городу, не к
макро-региону), `first_name`/`last_name`. `role` на `User` — третье
значение, `"ambassador"`, помимо `"admin"`/`"user"`.

**Два независимых, параллельных пути входа для амбассадора** — специально
не единственный, из-за сетевой блокировки VPS→Telegram (см. Deploy ниже):
- **Telegram-бот/мини-апп** — [app/routes/telegram_bot.py](app/routes/telegram_bot.py)
  (`POST /telegram/webhook`, секрет в `X-Telegram-Bot-Api-Secret-Token`) +
  [app/services/telegram_bot_service.py](app/services/telegram_bot_service.py)
  (диалог саморегистрации: имя текстом → город инлайн-кнопками из
  `sales_options_service.get_cities()`, без aiogram/FSM — состояние читается
  из самих nullable-полей `User`, отдельная таблица под FSM для
  двухшагового диалога избыточна) + [app/routes/ambassador_app.py](app/routes/ambassador_app.py)
  (`/ambassador/app/*`, мини-апп внутри Telegram WebView). Аутентификация —
  **header-based**, не cookie: `Authorization: tma <initData>`,
  [app/telegram_auth.py](app/telegram_auth.py)`::get_current_ambassador`
  проверяет HMAC-подпись initData секретом бота (`TELEGRAM_TOKEN`) и смотрит
  `telegram_id`/`role` в `User`. Поэтому эти пути — в `CSRF_EXEMPT_PATHS`
  (см. CSRF выше): обычный double-submit cookie тут неприменим по
  построению, ambient-cookie не участвует в аутентификации вообще.
- **Браузер** — [app/routes/ambassador_web.py](app/routes/ambassador_web.py)
  (`/ambassador/*`: `/profile`, `/visit`, `/leaderboard`), обычная
  cookie-сессия через `/auth/login` (тот же `PasswordToken`-флоу, что у
  `user`/`admin` — `/auth/login`/`/auth/set-password` не смотрят на роль
  вообще, изменений не потребовалось) и обычный CSRF (не в `CSRF_EXEMPT_PATHS`,
  формы полагаются на глобальный `csrf.js`). `telegram_id` при создании
  амбассадора в `/admin/users/new` теперь **опционален** — обязателен был
  только исторически, до появления браузерного пути. Свой минимальный
  layout [base_ambassador.html](app/templates/base_ambassador.html) (по
  образцу `base_auth.html` — без сайдбара, амбассадору не должна быть видна
  навигация по аналитике/админке, к которой у него всё равно нет доступа).
  `require_ambassador` в [app/auth_deps.py](app/auth_deps.py) (`role in
  ("admin", "ambassador")`) — только для этого, браузерного пути; Telegram
  использует отдельный, header-based `get_current_ambassador`, не эту
  зависимость.

  Оба пути пишут в одни и те же поля `User` (`first_name`/`city`) — кто
  раньше зарегистрируется (бот или браузер), у того и берутся данные,
  второй путь просто видит «уже зарегистрирован»/анкета не показывается
  повторно (`_profile_complete()` в `ambassador_web.py` — `first_name` и
  `city` оба заполнены).

**Бизнес-логика визита и лидерборда — в сервисах, не завязана на источник
запроса**, поэтому у неё три вызывающих (Telegram, браузер, обычный веб)
почти без дублирования:
- [app/services/ambassador_service.py](app/services/ambassador_service.py)
  — `get_visit_options(db, city)` (клиенты/типы точек/товары с ABC-бейджем
  по сегменту, угаданному из типа точки — `abc_service.guess_default_segment()`)
  и `create_visit(db, ambassador, city, client, sale_type, product_ids)`
  (валидирует `city == ambassador.city`, `client`/`sale_type` — реальные
  значения из `Sale` этого города, `product_ids` — активные товары).
- [app/services/leaderboard_service.py](app/services/leaderboard_service.py)
  — `get_leaderboard(db, selected_months=None)`: только **активные**
  (`is_active=True`) амбассадоры — отключённый через `/admin/users`
  пропадает из лидерборда целиком, вместе со своими визитами (не строка с
  занулёнными цифрами), фильтр по месяцу — через `Visit.created_at`
  (`parse_month()`, тот же парсер, что у `Sale.month`, хотя формат тут
  всегда один). `get_leaderboard_months()` — список месяцев для пикера,
  не учитывает активность амбассадора (можно выбрать месяц, где визиты
  были только у отключённого — даст пустую таблицу, не ошибку). Вызывается
  из `/leaderboard` (веб, `require_analyst`), `/ambassador/leaderboard`
  (браузер) и `/ambassador/app/leaderboard` (Telegram, без фильтра по
  месяцу — там нет `month_year_grid()`, чистый JS-фетч).
- [app/services/visit_effectiveness_service.py](app/services/visit_effectiveness_service.py)
  — третья вкладка на «Анализе по клиентам» (`?tab=visit_effectiveness`):
  сверяет продемонстрированные визитом ароматы с тем, что клиент заказал
  (`Sale`) в том же периоде. Причинность (заказ строго после визита) не
  проверяется — `Sale.month` хранит только месяц, точность не позволяет.

Удаление пользователей (`/admin/users/{id}/delete`) блокирует удаление
амбассадора с историей визитов — детали в разделе Auth выше («Удаление
пользователей»), тот же принцип, что и фильтр лидерборда по активности:
`Visit` считается реальными бизнес-данными, не служебной записью.

## Deploy

`main` → GitHub Actions CI ([.github/workflows/ci.yml](.github/workflows/ci.yml): ruff + black
--check + pytest на sqlite) → при зелёном CI автоматически триггерится
[deploy.yml](.github/workflows/deploy.yml) по SSH на VPS: git reset --hard на прод-ветку,
бэкап Postgres в `/home/ubuntu/sarma_backups` (хранится 14 дней), `alembic upgrade head` внутри
контейнера, `docker compose up -d --build`. Ручного деплоя нет — пуш в `main` с прошедшим CI
достаточен.

Локальный `main` часто уходит вперёд `origin/main` на несколько коммитов, пока идёт сессия
работы — не забывать `git push`, если требуется деплой или продолжение с другой машины.

**CI не видит локальный `.env`** — тесты, которым нужен `TELEGRAM_TOKEN` (initData
HMAC-подпись, горизонт 13), не должны полагаться на реальный `.env` (в `.gitignore`,
только на машинах разработчиков): `tests/conftest.py` ставит
`os.environ.setdefault("TELEGRAM_TOKEN", ...)` тестовым значением до
`load_dotenv()` — иначе зелено локально, красно в CI (поймано именно так при
первом деплое горизонта 13, 2026-08-17).

**SSH на VPS (`ubuntu@178.154.246.148`) принимает только ключи, пароля нет.**
Если с текущей машины ключа ещё нет — **не пытаться добавить его через
метаданные `ssh-keys` в консоли Yandex Cloud для уже существующей ВМ, это
не работает в принципе**, не баг и не вопрос прав: поле в редакторе метаданных
read-only для любого владельца, официальная документация Yandex Cloud
(`vm-connect/ssh#vm-authorized-keys`) прямо говорит, что добавление ключей
через метаданные поддержано только при создании ВМ, не постфактум. Рабочих
способов добавить ключ на уже поднятую ВМ без даунтайма — нет: нужен либо
существующий SSH-доступ (тогда просто дописать `~/.ssh/authorized_keys`),
либо serial-консоль + загрузка в GRUB rescue (перехватить загрузку,
`init=/bin/bash`, перемонтировать root на запись, дописать ключ,
перезагрузить) — рабочий, но с даунтаймом CRM на время перезагрузки, делать
осознанно, не как первую попытку. `user-data` (cloud-init) в метаданных
редактируется, но `ssh_authorized_keys` оттуда обычно применяется только на
первом реальном старте инстанса — дописать туда ключ безопасно (не помешает),
но полагаться на то, что он сам подхватится, нельзя.

После добавления новой переменной в прод `.env` — **этого недостаточно само
по себе**, нужны оба шага: (1) саму переменную явно дописать в секцию
`environment` сервиса `web` в [docker-compose.yml](docker-compose.yml)
(`.env` только подставляет значения в `${...}`, но список того, что вообще
пробрасывается в контейнер, задаёт сам compose-файл — забыли на этом шаге
`TELEGRAM_TOKEN`/`TELEGRAM_WEBHOOK_SECRET` при горизонте 13, мини-апп не
поднимался, хотя `.env` был заполнен верно и `docker compose exec web env`
показывал, что переменных внутри просто нет); (2) `docker compose up -d
--build --remove-orphans`, не `restart` — переменные окружения читаются
только при пересоздании контейнера. Оба шага деплоятся обычным путём (правка
`docker-compose.yml` коммитится и пушится в `main`, ручной SSH — только для
самого `.env`, который не в git).

SSH на VPS: из нескольких ключей в `~/.ssh/` на машине пользователя рабочим
оказался `guidebot_deploy`, не `github_deploy` (тот выдаёт `Permission
denied`) — не факт, что не сменится, но с этого начинать проверку в следующий
раз.

**Исходящий HTTPS к Telegram (`api.telegram.org:443`) с этого VPS может быть
заблокирован на сетевом уровне — это не баг кода.** Пойманный симптом:
`curl`/`setWebhook` зависает без ответа, при этом `ping` до того же IP
проходит мгновенно — типичная картина блокировки именно TCP:443, не общий
сбой сети. Диагностика: если `setWebhook`/`getWebhookInfo` не отвечают —
сначала проверить `sudo docker logs dziro_bot --tail=20` (или `guide_bot-bot-1`)
на этом же сервере — оба независимых бота используют long polling, и если
там тоже свежие `TelegramNetworkError`/таймауты, значит проблема сетевая и
общая для всего хоста, не специфика sarma-crm — чинить код в этом случае
бессмысленно, ждать восстановления доступа или заводить прокси/VPN для
исходящего трафика к Telegram (горизонт 13 ROADMAP.md, доп. заход, 2026-08-17).
